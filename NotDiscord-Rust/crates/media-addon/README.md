# Motor multimedia Rust

`notdiscord-media-addon` compila un `cdylib` N-API que se carga en el Electron main-compatible del motor tercero `discord_voice.node`. Toda lógica propia de protocolo, pipe, audio/settings, estado, MLS/DAVE, temporizadores, cámara/pantalla y estadísticas está en Rust. `host/main.cjs` es sólo frontera declarativa del runtime (requiere objetos tercero y llama `run`); no carga los helpers JavaScript de referencia ni C#.

Compilar con `cargo build --release -p notdiscord-media-addon`; copiar `target/release/notdiscord_media_addon.dll` como `NotDiscord.Media.node`. El host necesita el runtime Electron compatible existente y sus DLL/pak; en `resources/app/` instalar `host/package.json` y `host/main.cjs`, sin conservar `resources/app.asar` anterior. No ejecutar el motor en Node stock: aborta en callbacks MLS/V8.

La aplicación Rust crea primero un named pipe Windows current-user-only y verifica el PID conectado. Inicia `NotDiscord.Media.exe` sin shell ni ventana y con:

- `NOTDISCORD_NATIVE_ROOT`: directorio del runtime tercero con `resources/standalone_modules/discord_voice/discord_voice.node` y DLLs.
- `NOTDISCORD_RUST_ADDON`: ruta absoluta a `NotDiscord.Media.node`.
- `NOTDISCORD_MEDIA_PIPE`: `\\.\pipe\NotDiscord.Media.<GUID>`.
- `NOTDISCORD_MEDIA_DATA`: directorio multimedia aislado.

Eliminar `ELECTRON_RUN_AS_NODE`/`NODE_OPTIONS`/`NOTDISCORD_MEDIA_PROBE` del entorno hijo; descartar stdout/stderr. No se crea BrowserWindow ni interfaz original. `Prepare-Host.ps1` instala el staging independiente y escribe `runtime.json` con rutas relativas a la aplicación; el paquete también conserva rutas relativas.

Contrato UTF-8 JSON por línea: `{id,command,params}`, respuesta `{id,ok,result}` o `{id,ok:false,error:{code,message}}`. Frame 1 MiB, cola 32, errores saneados. Se conservan los 20 comandos de referencia: `capabilities`, `stats`, `listDevices`, `configureAudio`, `ptt`, `startMicTest`, `stopMicTest`, `listCameras`, `startCamera`, `stopCamera`, `setDevices`, `connectVoice`, `disconnect`, `mute`, `deafen`, `setVolume`, `listSources`, `startShare`, `stopShare`, `shutdown`. Se añaden `startCameraPreview`, `startScreenPreview`, `stopMediaPreview` (y el alias `stopCameraPreview`), `setVideoVisible`, `setVideoQuality`, `focusVideo`, `watchStream` y `stopWatchStream` para vídeo.

Eventos: `ready`, `voiceState`, `shareState`, `cameraState`, `participant`, `speaking`, `mediaStage`, `micTest`. Estados de voz `connecting`, `negotiating`, `waiting-peer`, `connected`, `disconnected`, `error`; payload con `kind`, `transportReady`, `encryptionReady` y voz `cameraAvailable`. `connectVoice` y `startShare` devuelven `session`; los eventos de estado incluyen `mediaSession` para rechazar eventos de sesiones antiguas. La aplicación debe seguir usando transporte local y cifrado real por separado. `shareState:paused` conserva sólo fuente/calidad/audio previamente seleccionados; Stop cancela reanudación.

Sensibilidad: `configureAudio` acepta `inputSensitivityDb` entre −100 y 0 dB (predeterminado −40). El mismo valor se pasa a VAD nativo y al indicador de voz local; se conserva el modo PTT independiente. El evento `inputLevel` proporciona `level` lineal normalizado, `db` y `speaking` desde el callback nativo, con un máximo de una actualización cada75ms. El estado remoto speaking procede del callback nativo del decodificador, no sólo del anuncio WebSocket.

La prueba local admite `startMicTest {token,settings}` con los mismos ajustes de audio; `stopMicTest {token}`. Los tokens positivos son opcionales para clientes anteriores y monótonos en la aplicación; un Stop viejo no detiene una prueba nueva. Antes de abrir captura/loopback se fuerza silencio y ensordecimiento en la conexión nativa, se cancela GoLive y se bloquean todos los caminos de mute/PTT/readiness mientras la prueba está activa. Stop apaga primero el loopback y sólo entonces restaura la elección previa de silencio/ensordecimiento; si falla, el controlador cierra el host. El máximo es30s. Cerrar/reemplazar el diálogo también solicita Stop. Una prueba nunca crea una llamada nueva.

Cámara y pantalla salientes se pueden seleccionar estando solo. La interfaz conserva esa selección explícita por 90 s, permite cancelarla y espera DAVE antes de solicitar la captura saliente; entrar en llamada no elige una fuente automáticamente. `startCamera`/`stopCamera` y `startShare`/`stopShare` aceptan token de cancelación. `cameraState` incluye `token` y `mediaSession`, evitando eventos de selecciones antiguas. La elección explícita de una cámara o fuente inicia automáticamente una única vista previa local; cambiar de selección reemplaza la anterior y cerrar el selector solicita `stopMediaPreview`. La vista previa no activa broadcast ni crea una conexión de voz. Confirmar cámara conserva y promueve el mismo sink a la sesión saliente; confirmar pantalla conserva la fuente elegida hasta que el callback de la emisión real la reemplaza. Cancelar la vista previa no detiene una captura saliente ya promovida.

`setVideoOutputSink(streamId, callback, true)` entrega `{width,height,data:Uint8ClampedArray}` RGBA; cada callback confirma `signalVideoOutputSinkReady(streamId)`, también al descartar frames. La aplicación usa un segundo pipe privado `NOTDISCORD_VIDEO_PIPE`, mismo SID/PID comprobado, y cabecera binaria NDVF de 36 bytes (versión, id, secuencia, dimensiones, longitud). Los píxeles nunca pasan por JSON ni disco. Se mantiene sólo el último frame por suscripción: máximo 4, máximo 8 MiB por etapa de cola, 640×360 a 12 fps por tile y un seleccionado a 1280×720/24 fps. Las texturas se reutilizan. Ocultar o cerrar la vista elimina sinks, pausa decodificadores y libera buffers/texturas; cerrar una preview sin emisión apaga la entrada de vídeo.

La cámara remota conserva `videoSsrc(s)` al actualizar audio y negocia `videoDecoders`. El callback nativo aporta el streamId real. Ver una pantalla solicita Gateway op20 y crea una sesión DAVE separada con `streamUserId` del propietario, siempre receive-only y silenciada para envío; cerrar elimina sólo esa sesión local; no envía op19 para detener la emisión del propietario. Eventos `videoStream` y `watchState` llevan sólo metadatos, nunca RGBA. Se limita a dos pantallas recibidas y cuatro vídeos visibles; se puede cambiar el vídeo enfocado. La prueba de la emisión/recepción con una cuenta real continúa separada de las pruebas sintéticas.

`capabilities` y `stats` sin sesión no inicializan motor/dispositivos. `run` exige Electron y pipe con prefijo/GUID válido. Las funciones N-API sólo se invocan en main-thread mediante TSFN; Tokio nunca recibe objetos/envN-API.

Pruebas Rust locales: `cargo test --workspace`. `Test-Host.ps1` verifica el addon de producción dentro del host real: capabilities/stats/shutdown, nativeInitialized:false y salida 0 (7 comprobaciones). Las pruebas de vídeo cubren RGBA, cabeceras, límites, slots, pipe real sintético, PID, detach, texturas, preview explícita y sesiones receive-only, incluidos fallo/reintento y eventos viejos.

Para comprobar la frontera MLS sin cuenta ni hardware, compilar por separado `cargo build -p notdiscord-media-addon --release --features native-probe`, copiar esa DLL como `.test-bin/NotDiscord.MediaProbe.node` y ejecutar `Test-NativeMls.ps1`. El probe usa captura falsa y UDP localhost; comprueba el callback asíncrono y el ArrayBuffer del paquete MLS sin persistir bytes. Después compilar **sin** esa feature y desplegar esa DLL de producción. El resultado acreditado es 392 bytes y 7 modos AEAD; ver `evidence/native-mls-probe.json`. Esto no demuestra audio remoto; confirmar llamada/cámara/pantalla con otro cliente requiere prueba funcional.

La vista previa de ventana usa `getSingleWindowPreview(handle,640,360)` con retorno Promise de un array de fuentes; configura `setPreviewsUseWgc(false)` después de inicializar el motor. El retorno real observado es `data:image/bmp;base64` (también se admiten PNG/JPEG). La decodificación queda dentro de Rust: máximo 2 MiB codificados, imagen de hasta 1280×720 y 8 MiB de asignación, después escala a 640×360. Sólo se consulta una selección, con una petición pendiente y separación de 750 ms; al cancelar se invalida el token. Los datos nativos codificados nunca pasan al pipe JSON ni a disco. El resultado entra en el mismo canal binario RGBA acotado.

Los errores de códec, sink o recepción de un participante producen metadatos `videoStream`/`videoError` de ese stream y conservan el audio. Un fallo irrecuperable del proceso limpia conexiones, buffers y épocas; la interfaz permite iniciar un host nuevo si los archivos del runtime siguen disponibles. Durante detach la referencia N-API permanece accesible para un último ACK síncrono, sin mantener un préstamo de RefCell durante la llamada nativa; se libera tras retornar.

`Test-OwnedPreview.ps1` verifica el recorrido real de vista previa sin cuenta ni hardware: una compilación `native-probe` crea su propia ventana Win32 de cuatro colores, valida HWND/PID/clase y permite exclusivamente `getSingleWindowPreview` de esa identidad. No usa catálogo nativo de otras ventanas ni captura escritorio, cámara o micrófono. El gate final observó BMP nativo 384×258, RGBA binario y cuatro muestras opacas exactas, cierre de ventana/sinks/buffers, ACK reentrante y salida 0. `NativeCatalogVerified=false` distingue la identidad propia comprobada del catálogo nativo no consultado. Informe: `evidence/owned-window-preview-probe.json`; DLL de prueba SHA256 `8030BA575F538A73F22B4B63A86ACC10CB9DEF3F6864B3E46A86AD30A546BBD8`. No prueba envío ni recepción con un segundo cliente. Distribuir siempre el addon compilado sin `native-probe`.

Observed causes and implemented changes
--------------------------------------
1. The current provider is Klipy. The old media allowlist omitted it. Added only
the observed/public media hosts and canonical /gifs share pages. Protocol-relative
provider sources are normalized to HTTPS; suffix-host tricks remain rejected.
2. GET GIF catalogue limit12 and24 returned HTTP400. Validated20,50,100 return200.
Endpoint now normalizes to20/50/100. UI grows20→50→96, retaining max96. The small
response cache retains a full accepted remote page, then trims local display;
it cannot cache24 and silently reuse those24 for a48-result request.
3. Windows WPF needs actual GIF data. media_format=gif with limit20 returned20
GIF thumbnails for both trending and search. The WebM experiment returned video
sources instead; the client retains media_format=gif.
4. Settings protobuf base64 was truncated at4096 characters by a URL helper.
Read the whole settings string, keeping the existing1MiB decoded size limit.
5. Existing Discord favorites are read only. New stars remain local per account.
Added local .txt/pasted-link import as an alternative; max100 saved local links,
256KiB input,500examined lines. No settings writes or cloud synchronization.
6. Known catalogue canonical-page→gif_src pairs use a128-entry,15minute cache.
The metadata fallback does not execute scripts or guess media identifiers.
7. Windows banners receive sender/group/channel title, ~50-grapheme preview,
and sender avatar when available. Native48px icon reuses bounded thumbnail cache.
8. Per-user Start Menu shortcut and AppUserModelId registration set source display
name NotDiscord and the requested Discord icon, pointing to the actual executable.

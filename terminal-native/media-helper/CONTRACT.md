# Standalone media helper — experimental integration

Launch `media-host/runtime/NotDiscord.Media.exe` with no arguments and no shell. Create a current-user-only Windows named pipe first, verify the connecting process ID, and pass its full name through `NOTDISCORD_MEDIA_PIPE=\\.\pipe\NotDiscord.Media.<GUID>`. The host validates this exact prefix and a 32- or 36-character GUID, deletes the environment variable, and connects within ten seconds. All protocol traffic uses that duplex pipe; discard stdout/stderr. The child must be owned by the desktop process; close/kill its tree on application exit. No HTTP listener exists.

The host is a minimal Electron main process, without BrowserWindow, web content, or Discord's original UI and bundles. It uses the private runtime already in this project: its executable is a separate copy and immutable DLL/pak dependencies use hardlinks. Its isolated data directory is `terminal-native/data/media-host`. The voice addon is read from `../../native-candidate/runtime`; no account profile or account token is read. A call-specific voice token is supplied through the private pipe only and is never persisted or returned. Plain Node remains usable for synthetic unit tests, but real engine initialization fails closed: its native asynchronous MLS ArrayBuffer callback aborts outside the matching Electron host.

Input: one UTF-8 JSON object per line, `{ "id": "request-1", "command": "...", "params": {} }`.

Reply: `{ "id": "request-1", "ok": true, "result": ... }` or `{ "id": "request-1", "ok": false, "error": { "code": "...", "message": "..." } }`.

Unsolicited events: `ready`, `voiceState`, `shareState`, `cameraState`, `participant`, `speaking`, `mediaStage`, `fatal`. `mediaStage` contains only a fixed stage literal and kind (`native`, `voice`, `share`), never arguments or identifiers. Voice states are `connecting`, `negotiating`, `waiting-peer`, `connected`, `disconnected`, `error`. `transportReady` means native UDP and authenticated transport setup succeeded. `encryptionReady` and the helper's internal `connected` require an accepted DAVE initialization/transition. `cameraAvailable` additionally requires negotiated video support. The native connection starts send-muted and stays send-muted until DAVE is ready. An error never contains the raw server frame or native exception. Unknown frame bodies are never logged. Participant events `{userId,present,video?}` and deduplicated speaking events `{userId,self,active}` carry the current call's identities through the private UI pipe only, never into diagnostics/stats.

A sole member may have an unestablished local MLS group until another participant arrives. After authorized call transport setup, `waiting-peer` enables the selected local microphone and local VAD feedback plus mute/deafen/PTT controls, with no network speaking announcement or send-unmute before DAVE. The initial 30-second transport timer ends at transport readiness. A separate 30-second DAVE timer runs only while another participant is present and encryption is pending; a peer leaving cancels that timer. The desktop maps transport-ready waiting/negotiating states to usable local call controls, while `VoiceEncryptionReady` independently gates camera, screen capture and automatic video activation. No protocol-zero fallback exists.

## Commands

- `capabilities`: loads the local addon but does not initialize devices or connect. `voice`, `screenShare`, and `camera` indicate implemented code paths in the compatible host. `screenReceive` and `cameraPreview` remain false. Global `verifiedLive:false` does not assert all paths/devices have passed live validation; the user separately confirmed voice and sharing before the camera addition.
- `stats`: no parameters. Does not load/initialize a native engine or create a session. Returns `{sanitized:true,sampledAtUtc,voice:null|REPORT,share:null|REPORT}`. An existing native connection is sampled with `getFilteredStats(7, callback)` (or `getStats` when available), with a two-second timeout. Unavailable numeric/string measurements are `null`, never requested UI settings. Each report contains `available`, `state`, `encryption:{negotiatedByHelper,nativeDaveProtocolVersion,nativeDaveEnabled}`, `transport:{bytesSent,bytesReceived,packetsSent,packetsReceived,rttMs,sendBandwidthBps,outboundEstimateBps,inboundEstimateBps,decryptionFailures}`, `outbound:{audio,video:[]}` and `inbound:{audio:[],video:[]}`. Audio items contain codec, bytes, packets, packetsLost, bitrateBps (outgoing), sampleRateHz, audioDetected, framesCaptured/Rendered (outgoing), and encrypt/decrypt counters in `crypto`. Outgoing video includes native width/height, fpsInput/fpsEncode, framesSent/Encoded, bytesSent/packetsSent, loss, bitrate/target bitrate, CPU/bandwidth limitation flags and crypto counters. Incoming video has width/height, fpsNetwork/fpsDecode/fpsRender, framesReceived/Decoded, bytesReceived/packetsReceived, bitrate and crypto counters. Only known codec names are returned. No IDs, SSRC, addresses, device labels, window titles, raw JSON, exception text or credentials cross the stats pipe. `interval` is unknown on the first sample; after a second sample at least 100 ms and at most five minutes later it contains elapsed durationMs and bitrate/packet rates derived from transport counter deltas; reset counters yield null. Only four sanitized counters are retained. There is no polling timer: call on demand, normally twice at least five seconds apart. Native encryption success and received data counters provide evidence of processed media but do not prove receiver audibility or display quality. An unavailable report has `available:false`, a fixed reason code, and null measurements.
- `listDevices`: explicitly initializes the native engine and returns `{input:[{id,name,index,type}],output:[...]}`. The UI must request this only for device settings or a call.
- `setDevices`: `{inputId?,outputId?}`; ids come from `listDevices`. Device/settings changes preserve already-authorized local input while waiting for a participant. Idle configuration keeps input disabled.
- `configureAudio`: validated device, volume, processing and PTT settings; it does not authorize idle capture. `ptt:{active:true|false}` preserves the held key during local readiness without releasing the DAVE send-mute gate.
- `listCameras`: returns `[{id,name}]` from native GUIDs, without selecting a camera. The UI calls it only after the camera button is explicitly clicked during a call. Labels and GUIDs are ephemeral picker data, not diagnostics.
- `startCamera`: `{deviceId}` from this helper's `listCameras` in the preceding ten minutes. Requires connected encrypted voice and a negotiated video encoder/server SSRC. Voice Identify advertises an **inactive** video stream; negotiation alone never selects a camera or calls `setVideoBroadcast(true)`. This command explicitly selects the chosen GUID and enables broadcast at requested 720p/30 FPS. It waits up to ten seconds for native self-video activation before replying `{state:"active",verifiedReceiver:false,preview:false}`. `cameraState` is `preparing`, `active`, `stopped`, or `error`; active describes native stream activation, not a measured frame count or receiver display. Failure disables the device, preserving voice where possible. The desktop sends main-Gateway `self_video:true` only after activation, and preserves that flag when changing mute/deafen.
- `stopCamera`: disables voice-connection video broadcast, selects native video device `disabled`, and announces inactive video SSRC. The desktop sends `self_video:false`; camera state resets on disconnect, helper failure and logout. Camera controls do not modify the separate Go Live capture connection. There is no local preview or incoming-video presentation in this version.
- If an active camera later reports self-video SSRC zero, the helper disables its device/broadcast and emits `CAMERA_SOURCE_ENDED`, rather than waiting forever in preparing. The desktop also synchronizes `self_video:false` for asynchronous stop/error events, serialized with explicit controls and guarded against a replaced call or restarted camera. The targeted synthetic loss test includes a reentrant zero-SSRC callback during native stop; it confirms one stop, no return to preparing, and preserved encrypted voice. No real camera was activated for that test.
- `connectVoice`: `{userId,guildId?,channelId,sessionId,voiceToken,endpoint,selfMute?,selfDeaf?}`. The desktop owns the main Discord Gateway and must wait for both its own `VOICE_STATE_UPDATE` and `VOICE_SERVER_UPDATE`. In DMs the server ID is the channel ID. This command returns `connecting` immediately; observe subsequent state events. A new channel/session needs a new request with fresh voice credentials.
- `mute` / `deafen`: `{value:true|false}`. The desktop also sends the corresponding main-Gateway voice state update.
- `setVolume`: `{target:"input"|"output"|"user",value:0..400,userId?}`. User volume requires a native connection. UI value is percent, default 100; the helper converts this to the addon ratio (100% = 1.0). Raw native volume must never receive the UI percentage directly.
- `disconnect`: stops voice and stream native connections and WebSockets; the desktop must also leave through the main Gateway. Send `shutdown` and terminate the helper after leaving to reclaim its native engine and thread memory.
- `listSources`: explicitly enumerates native screen/window sources and returns `[{id,name,type}]`. Images are discarded immediately; listing must happen only when the user opens the source picker. Verified with fake audio/video devices: this machine returned `screen-handle:<number>` and `window:<number>` IDs. Do not rewrite their prefix. `startShare` only accepts sources listed by this helper in the previous ten minutes.
- `startShare`: `{userId,channelId,rtcServerId,streamChannelId?,sessionId,voiceToken,endpoint,sourceId,quality:{height:720,fps:30},audio?:{enabled:true,loopback:true,pid:0}}`. Requires an already-connected voice session. The desktop must create a Go Live stream on its main Gateway and obtain a separate `rtcServerId`, token and endpoint from the stream events. Do not reuse the ordinary voice token. For stream Identify/MLS, the helper uses `streamChannelId` if supplied, otherwise `BigInt(rtcServerId)-1`, matching the retained original `StreamRTCConnection`; the real voice channel is retained separately. `sourceId` must be returned by `listSources`. A separate native connection and DAVE group are created; after encryption, `capture-requested` reports that capture was requested, not verified on the receiver. Optional audio is disabled by default: `{enabled:true,loopback:true,pid:0}` requests system audio; `{enabled:true,loopback:false,pid:SOURCE_PID}` requests audio for the selected window process. Only enable either after the user chooses audio sharing. The desktop can resolve a window handle with GetWindowThreadProcessId; do not infer a process ID from the handle. `audio-attached` confirms native attachment, not delivery. Accepted heights: 480/720/1080/1440, FPS: 15/30/60. UI controls do not grant account/server entitlements and negotiated results must be verified.
- `stopShare`: clears capture and destroys the stream connection. The desktop also deletes its Go Live stream through the main Gateway.
- A DAVE epoch-one reset withdraws encrypted readiness immediately. Active camera capture stops and requires an explicit new activation. Active screen capture and soundshare stop before native epoch preparation; `shareState:paused` retains only the same explicitly selected source, quality and audio choice. That selection may resume only after real DAVE readiness. Stop/disconnect clears the selection and prevents resumption. Intentional clear callbacks while paused cannot reactivate or fail it; a source-ended event while active fails closed. The native source-ended callback has no source identity, so a delayed old event after resumption can conservatively stop the current stream. The desktop exposes `ScreenPaused` and permits Stop while encryption is pending. Interrupted share setup also clears preparation flags even when encryption drops during its await.
- `shutdown`: destroys connections and exits. Pipe EOF/close/error also closes everything after queued commands finish. The helper uses no automatic retries with retained session credentials; obtain a fresh session via the desktop on errors.

## Offline verification performed

`node --test media-helper/test.cjs`: 31 tests cover protocol framing, endpoint validation, refusal of deprecated transport modes/DAVE downgrade, local-versus-encrypted readiness, time alone without a false timeout, peer join/leave timers, mute/deafen/PTT/VAD gating, nonzero transition execution, stale callbacks after epoch reset, screen/audio pause and cancellation, camera stop on reset, distinct stream RTC channel calculation, linear native volume units, credential redaction, strict stats projection, unknown measurements remaining null, and stats without loading the native engine. Camera fixtures also verify inactive negotiation, explicit activation, native video-state waiting, failure/disconnect cleanup and participant feedback. These fixtures do not load the addon or activate a real device/network. `research/SoloVoice.Readiness.Tests.cs` records 18 assertions against the current desktop assembly, including synthetic pipe responses for readiness loss during share setup and replacement attempts. `research/MediaJoin.Tests.cs` records six assertions with fake HTTP. `tests-media-recovery/result.json` records 17 assertions for real private-pipe rejection/cleanup and synthetic call-panel state, with zero native initialization stages. The 2026-10-20 results and source hashes are recorded in `research/SOLO-VOICE-20261020.txt`.

Earlier compatibility probes: child-process smokes with `capabilities`/`shutdown` and `stats`/`shutdown` emitted JSON only and exited. The former successfully loaded 104 addon exports with stock Node 24.19.0; the latter returned null sessions without loading the native engine. `research/probe-media-init.cjs` initialized fake audio/video devices only (no connections/capture) and confirmed codec capability callback format is a JSON string with `codec` fields. H264 and VP8 encoders were reported on this machine. `research/probe-media-sources.cjs` verified source enumeration with fake audio/video and discarded all names, handles and preview images; only anonymized schema/counts were saved.

User-reported live evidence: voice and outgoing screen sharing worked before this camera/UI change. Not yet established for this change: live camera delivery, reconnect behavior, every audio/device-driver combination, incoming-video rendering, or equal-quality CPU/RAM target. No new benchmarks were run. Do not equate synthetic callback tests with a real camera picture received by another client.

Host correction evidence (2026-10-18): `research/voice-mls-loopback.json` reproduces Node exit 134 with fake audio/video and a private loopback UDP listener. The epoch API accepts the original string arguments, but the asynchronous key-package result aborts with `Cannot create a handle without a HandleScope` at `napi_create_arraybuffer`. `research/media-host-mls.json` runs the same setup in the minimal Electron host, produces a 391-byte synthetic MLS key package and exits normally; no bytes of that package are persisted. `research/media-host-ipc.json` verifies capabilities/stats, shutdown and pipe EOF without initializing devices, both with exit 0. These are compatibility checks, not successful live-call evidence.
